# ADR-004：建设项目独立 MySQL 数据库

## 状态

Accepted；表前缀和物理模型约定已由
[ADR-005](ADR-005-采用统一hd_plt目标数据库模型.md)取代

## 日期

2026-07-17

## 背景

后端已确定使用 Java 与 MySQL。当前不存在必须接入的既有平台数据库，用户确认数据库由本项目自行建设。平台公共能力和临床研发管线属于同一项目，但不应与其他业务系统共享数据库实例、root 账号或应用账号。

## 决策

1. 本项目独立建设 MySQL 8.x 数据库，使用 InnoDB 和统一 `utf8mb4` 字符集/排序规则。
2. 开发、测试、生产环境隔离，测试不得连接生产。
3. 本ADR不再规定表前缀；最终统一使用 `hd_plt_`，详见ADR-005。
4. 数据库变更统一使用 Flyway，生产禁止 Hibernate 自动建表或改表。
5. 分离 `db_migration`、`app_runtime` 和 `db_readonly` 账号；运行账号不拥有 DDL、建用户或跨库权限，任何服务不得使用 root。
6. MySQL 不暴露公网；来源网络受限，跨主机连接启用 TLS，凭据由密钥/部署系统托管。
7. 生产启用自动全量备份、binlog、时间点恢复和异地/隔离保存，并定期执行恢复演练。
8. 项目负责数据库补丁、容量、慢查询、备份、恢复和故障响应，必须设置明确 Owner 与告警。

## 备选方案

### 接入公司已有业务数据库实例

优点：基础设施可能更快可用。

缺点：账号、容量、变更窗口、故障和备份边界容易互相影响；当前也没有必须接入的实例。

结论：不采用。

### 应用使用 root 或高权限账号

优点：开发方便，权限问题少。

缺点：应用漏洞可能升级为建用户、删库或跨库访问，违反最小权限原则。

结论：禁止。

### 生产由 Hibernate 自动更新表结构

优点：开发阶段省去迁移脚本。

缺点：变更不可审计、不可预演，可能锁表或破坏数据，难以回滚。

结论：禁止；统一使用 Flyway。

## 后果

正面影响：

- 数据、账号、备份、容量和发布边界清晰，不受其他业务系统直接影响。
- Flyway 与最小权限账号使结构变更可审计、可复现。
- 可依据临床管线实际负载独立优化索引和容量。

代价与约束：

- 项目必须具备真实数据库运维能力，不能只完成安装和建表。
- 需要承担升级、补丁、监控、备份和恢复演练成本。
- 生产拓扑仍需依据 RPO、RTO、预算选择单实例或高可用架构。

## 验证

- 应用账号无法建表、删库、建用户或访问其他数据库。
- 目标结构必须在上线前纳入Flyway；当前独立25表脚本的空库执行验证不能替代Flyway重复部署验证。
- 自动备份、binlog 和监控告警有效；备份能在隔离环境成功恢复。
- 测试环境无法连接生产数据库，数据库不暴露公网。
