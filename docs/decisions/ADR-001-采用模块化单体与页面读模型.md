# ADR-001：采用模块化单体与页面读模型完成前后端拆分

## 状态

Accepted（用户已确认 Java 后端、MySQL 及项目独立建设数据库）

## 日期

2026-07-16

## 背景

当前系统是一个纯 HTML/React 原型。账号、风险、管线配置、月报、团队、里程碑、排序和阶段覆盖等业务数据保存在浏览器 `localStorage`；权限、阶段回填、风险评分、月报完成率、Project 聚合和导出也在前端执行。

目标是让前端仅承担交互和渲染，后端成为数据、权限和字段展示口径的唯一真源。当前页面作为未来平台的业务 Tab，平台化前端边界由 [ADR-002](ADR-002-将临床研发管线建设为平台业务Tab.md) 约束。

## 决策

1. 后端采用 Java + Spring Boot 3.x 模块化单体，而非第一期微服务。
2. 对外使用版本化 REST API `/api/v1`。
3. 写 API 使用稳定领域资源；页面查询使用 BFF/Read Model 返回已授权、已计算、可展示的页面模型。
4. 后端返回字段标签、显示文本、语义状态、计算说明和允许动作，但不返回 CSS、DOM 或像素布局。
5. 项目独立建设和维护 MySQL 8.x（InnoDB、`utf8mb4`），作为业务唯一真源；浏览器仅保留纯 UI 偏好。具体运维边界见 [ADR-004](ADR-004-建设项目独立MySQL数据库.md)。
6. 权限使用userId、role和permission；角色范围仅为ALL或ASSIGNED_STUDY，后者由团队分配决定Study可见范围。
7. 风险评分、阶段状态、里程碑状态、月报完成率和导出统一复用后端领域服务。
8. 所有写操作使用事务、状态/更新时间条件校验和审计日志。
9. 不迁移原型 `localStorage` 数据；正式系统从空业务库和正式初始化字典开始。
10. 后端固定划分为 `api`、`common`、`domain`、`manager`、`repository`、
    `service` 和 `test` 七个 Maven 模块。`service` 是唯一启动和部署模块。
11. Domain 定义数据访问端口，Repository 实现端口；Manager 通过 Domain
    端口编排业务。Domain 不得依赖 Repository 实现，跨模块不得直接使用
    JDBC Mapper 或持久化对象。
12. 前端源代码独立放在 `frontend/` 工程。第一阶段 Maven 将
    `frontend/src` 打入 Service 可执行 JAR，保持同源单体部署；同时由
    `npm run build` 生成可独立发布的 `dist`，为未来 Nginx/CDN 部署保留边界。
13. 数据库物理模型、表前缀和数据范围实现以
    [ADR-005](ADR-005-采用统一hd_plt目标数据库模型.md)为准。

## 备选方案

### 继续使用前端通用 CRUD API

优点：后端开发量较小。

缺点：字段逻辑、聚合、权限和导出仍会散落在多个前端页面，无法实现口径单一；浏览器容易获取超出当前展示范围的数据。

结论：不采用。

### 后端直接返回 HTML 或 CSS 配置

优点：后端可完全控制页面输出。

缺点：服务端与具体前端布局强耦合，响应式设计、组件复用、可访问性和前端升级困难，也不利于 API 被其他客户端复用。

结论：不采用。改为返回不含样式的展示语义。

### 第一阶段直接拆微服务

优点：模块可独立部署和扩容。

缺点：当前领域关联强、事务多、团队和容量需求未证明需要微服务；会引入分布式事务、调用链、部署和数据一致性成本。

结论：不采用。先以模块边界约束单体，未来依据容量、团队所有权或发布节奏再拆。

### GraphQL

优点：前端可按需选择字段。

缺点：当前页面的聚合口径和字段权限复杂，仍需专门 resolver/read model；缓存、复杂度限制和字段级授权增加实施成本。现有需求更适合明确的页面查询资源。

结论：第一期不采用，REST 已足够。

## 后果

正面影响：

- 页面、接口和导出共享同一业务口径。
- 前端代码显著减少业务公式和越权风险。
- 数据可跨设备共享，并获得事务、并发控制、备份和审计能力。
- 模块化单体保留未来拆服务的边界，同时降低第一期复杂度。
- 后续拆分服务时，可以保留 API 契约和 Domain 端口，将本地 Repository
  实现替换为远程适配器，而不改写核心领域规则。
- 前端代码与 Java 启动模块解耦，但第一阶段仍保持单域名、单制品部署，
  不引入跨域和双发布流程。

代价与约束：

- 页面读模型与前端存在一定契约耦合，需要 OpenAPI 和契约测试管理。
- 后端查询会承担较多聚合，需要索引、查询计划和必要时的可重建投影。
- 不建设旧 JSON 兼容层，原型数据仅保留为自动化测试 fixture 和 UI 参考。
- 后续 API 变更应优先新增可选字段，不得随意删除或改变现有字段类型。

## 验证

- 前端不再包含风险评分、阶段回填、权限和完成率公式。
- `/pipeline-overview` 与月报导出对同一用户、同一筛选条件口径一致。
- 权限测试覆盖列表、详情、写操作和导出。
- 当前原型黄金样例在新后端得到等价结果，差异均有业务签字。
