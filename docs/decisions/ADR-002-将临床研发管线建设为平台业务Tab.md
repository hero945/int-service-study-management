# ADR-002：将临床研发管线建设为平台业务 Tab

## 状态

Accepted（平台化边界继续有效；前端技术栈和路由细节已由 ADR-006 取代）

## 日期

2026-07-16

## 背景

当前纯 HTML 页面同时包含登录、一级导航、账号管理和临床研发管线领域页面。未来产品需要发展为承载多个业务模块的平台，当前页面只是其中一个子 Tab。如果直接把现有页面整体嵌入平台，会出现重复登录、重复导航、两套账号权限和样式不一致。

## 决策

1. 建立平台前端壳，统一负责会话、一级 Tab、用户上下文、设计系统、通知、错误边界和埋点。
2. 当前业务注册为 `clinical-pipeline` Tab，稳定路由为 `/platform/clinical-pipeline/*`。
3. 管线 Tab 内保留管线总览、Study、月报、风险、团队、配置、导出和里程碑二级页面。
4. 当前原型的账号管理上移至平台管理模块；业务 Tab 只消费用户 ID、权限码和数据范围。
5. 第一阶段采用同一 React/TypeScript 仓库内的路由模块和动态 `import()`，不采用独立运行时微前端。
6. 平台公共 API 使用 `/api/v1/platform/**`；管线领域 API 使用 `/api/v1/clinical-pipeline/**`。
7. 平台壳与 Tab 通过版本化 `PlatformTabModule`、用户上下文、错误和设计 token 契约协作。
8. 因现有平台壳不存在，本项目一期交付最小平台壳；不等待其他平台项目，也不把工作台、消息中心等完整门户能力纳入一期。

## 备选方案

### 将当前页面作为 iframe 嵌入

优点：改造快、隔离直接。

缺点：会话、路由、焦点、响应式、无障碍和跨页面通信困难；用户仍会看到重复导航和不一致体验。

结论：不采用。

### 立即实施微前端

优点：可以独立构建和部署。

缺点：当前尚无独立团队和独立发布证据，会提前引入依赖版本、运行时隔离、公共组件治理和排障成本。

结论：第一阶段不采用。先稳定模块契约；满足独立团队、独立发布和契约治理条件后重新决策。

### 每个 Tab 建独立 SPA，仅通过链接跳转

优点：实现简单、边界明确。

缺点：页面切换刷新，用户上下文和设计系统容易分叉，难以形成统一平台体验。

结论：不采用。

## 后果

正面影响：

- 新增其他业务 Tab 时可以复用认证、导航、设计系统、请求层和权限入口。
- 当前管线模块边界清楚，未来具备升级微前端的可能，但不承担当前不需要的成本。
- 账号和权限成为平台公共能力，减少临床管线模块的安全责任和重复实现。

代价与约束：

- 必须先定义平台壳和 Tab 契约，不能直接按现有 HTML 页面结构逐块搬运。
- 当前页面的登录、一级导航和账号管理组件不能原样保留在业务模块。
- 平台公共包需要版本纪律，禁止业务模块绕过公共 `api-client` 和设计系统自行复制。

## 升级为微前端的触发条件

同时满足以下条件后再创建新 ADR：

- 管线 Tab 有独立负责团队和独立发布节奏。
- 平台能够治理共享依赖、模块版本、监控和回滚。
- 单仓统一发布已成为明确瓶颈，并有发布频率或故障数据支撑。
- 独立部署收益大于多运行时、依赖重复和集成测试成本。

## 验证

- `/platform/clinical-pipeline/*` 深链接和刷新可用。
- 管线模块懒加载失败可重试，异常不影响其他 Tab。
- 管线模块中不存在登录页、一级导航、独立账号管理和第二套 HTTP 客户端。
- 平台按权限决定 Tab 是否可见，后端对每个领域请求再次鉴权。
